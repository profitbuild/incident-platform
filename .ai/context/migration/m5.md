## Parts, in order

### M5.1 The queue's schema (#0-291), with an ADR
- **Issue types** (organisation level): `Feature`, `Task`, `Bug`, `Audit` (ADR-0063 G5).
- **One Project "Factory"** (organisation `profitbuild`), with these fields:

  | Field | Values |
  |---|---|
  | `Status` | Draft, Ready, In progress, In review, Changes requested, Blocked, Done |
  | `Priority` | P0, P1, P2 |
  | `Risk` | low, high |
  | `Complexity` | low, medium, high |
  | `Lease until` | date |
  | `Attempts` | number |
  | `Run` | text |

  Views: a board by Status, Ready ordered by hand, and a table grouped by parent. The Project's built-in workflow
  sets Done when an issue closes.
- **A Task's body:** Problem, numbered AC, hints and constraints, and last a fenced block:

  ```factory
  spec: v1
  feature: <n>
  touches: [...]
  risk: low|high
  complexity: low|medium|high
  holdout: [...]
  ```

  Scripts read only that block, which has a JSON Schema in `factory/schemas/task.schema.json`.
- **Dependencies:** the native blocked-by; no "Depends on" line.
- **The trust rule** (security reviews of #0-286). The fields split in two:
  - **The owner's inputs**, trusted only when last set by the owner or `bc-app`: body, title, `Priority`,
    position, labels the owner sets, blocked-by edges, parent link, and the move from `Draft` to `Ready`. A blocker
    counts as closed only when a merged PR's `Closes` or the owner closed it, since builder-app and review-app hold
    Issues write too.
  - **The dispatchers' state**, which they write and read back: `In progress`, `Lease until`, `Attempts`, `Run`,
    `Blocked`, `needs-owner`.

  These rules close the gap between the two:
  - a `Ready` set by builder-app is accepted only as the return of a lease the dispatcher recorded itself, on an
    issue whose `Ready` the owner or `bc-app` had set before. A `Ready` set by any other app, review-app included,
    is refused. So no key of an app can make a `Draft` runnable;
  - **"changes requested" is derived from GitHub, from two sources**, each bound to its author:
    - `factory/review` = failure, bound to review-app by `integration_id`, on the PR's head (from M6);
    - a PR review in state `CHANGES_REQUESTED` by the owner's login on the PR's head. This is M5's own channel,
      while the owner reviews with `/review` (ADR-0063 D3), and it stays the owner's from M6 on.

    The Project field mirrors them for the board and is never read as input;
  - the dispatchers never read comments by anyone else.

  Two notes on the rules above:
  - **Spike first:** whether GraphQL names who last changed a ProjectV2 field value and a card's position
    (`userContentEdits` covers the body only). Where it does not, the dispatcher keeps its own record of the last
    `Draft`→`Ready` seen with its actor (from the issue's timeline events, if they name it), or the move to `Ready`
    is made only by `bc-app` on the owner's "ok", and an app's write to an input field stops the task as `Blocked`.
  - The organisation's interaction limit (collaborators) lasts a chosen time, not forever. It is renewed by the
    owner's calendar, and the trust rule stands without it.
- **What stays in the repository:** ADRs, `.ai/`, the audit's escape markers (`**Fixes:**`/`**Escaped from:**`,
  ADR-0055) and the owner's audit decisions.
- **Where:** GitHub (owner), `factory` (the schema), an ADR here.

### M5.2 The move (#0-292)
- **What:** one script (`scripts/factory-admin/backlog-to-issues.rb`):
  - turns every open `### 0-N` section into a `Task` (or `Bug`), titled `[0-N] <title>`, labelled `legacy`;
  - takes Status, Priority, Risk, Complexity and Touches from the section's fields, and `Depends on` as
    blocked-by;
  - keeps its text as the body, with the `factory` block appended.

  First a dry run into a test repository, then everything at once. After it, the two files get a header: "frozen
  YYYY-MM-DD, the queue is the Project". `migration.md`'s references move to the issues, or this map freezes with
  the files.

  The `/ready` skill and `ready-checker` write to an issue from here on (ADR-0063 G3). `.ai/plan/queue.md`,
  `check-queue.sh` and `/plan-backlog` are removed: the order is the Project's. `CLAUDE.md`'s conventions for backlog
  items move to the issue template.
- **Where:** incident-platform (owner-only `scripts/factory-admin/`, `.claude/`, `.ai/plan/`), GitHub.
- **Check:** the script's test turns three sample sections, one with a dependency, into the expected issues.

### M5.3 Dispatcher v1 (#0-293)
- **Choice, in this order:**
  1. its own PRs whose head has `factory/review` = failure (by review-app), the owner's `CHANGES_REQUESTED`
     review, or a red CI;
  2. PRs whose base moved (**rebase** work: rebase in the container, `--force-with-lease` to `factory/**`, M3.1's
     path);
  3. `Ready` with `Priority: P0`;
  4. the rest of `Ready` by Priority, then by card order.

  A task is taken only when every blocked-by is closed (by a merged PR or the owner, M5.1), its `touches` do not overlap an open PR's or a running
  task's, open PRs number fewer than the WIP limit (2), and a slot is free. P0 never interrupts a running task.
- **Claim:** Status `In progress`, `Lease until` +2h, assignee builder-app, a comment with the `runId`, then a
  re-read to check it is still ours. The sweeper returns an expired lease to `Ready` with `Attempts`+1, and two
  failures give `Blocked`, the `needs-owner` label and a notification. `Changes requested` → `In review` comes after
  the fix's push.
- **Two slots, one VM user and daemon each** (#0-285, ADR-0063 as amended for the new product, R1; was: two slots on
  `factory`'s daemon, G1-b phase 1).
  The VM grows to 16 GiB (not 20: the owner's host has 32 GB), each slot user's slice limited so one build cannot
  starve the other. `FACTORY_SLOTS=2`. The CI stays on GitHub's runners, so no CI VM takes the Mac's memory (ADR-0063
  as amended for the new product, R2, R4). M2.5's per-task lock and `FACTORY_SLOTS` carry it, with M3.4's
  (#0-285) sweep scope, orphans and Maven cache layout.
  **The proxy for a second slot (from the review of #0-313's VM side, 2026-11-23):**
  - the task image lets its container reach only the first of `PROXY_PORTS` (`.devcontainer/factory-proxy`, a file
    of the image: `task.json` carries no `build.args`, ADR-0062 point 4). A second slot's port needs a way to its own
    container that stays outside that closed table, decided before `FACTORY_SLOTS=2`;
  - a port of the proxy's address is free to bind for any uid while the dispatcher has not bound it (ports from 1024,
    iptables filters no `bind()`): a task of one slot could listen on the other slot's port before its run and get
    that task's token and prompts. The dispatcher binds every slot's port before any task starts, or refuses a run
    whose bind fails; until #0-285 the fresh-VM marker allows one run per VM, so this cannot happen yet.
- **Required checks strict** on `main` (#0-264's first half), so a PR is tested on the current base.
- **Trailers:** `Task: #<n>` and `Feature: #<parent>` join `Factory-Run`/`Factory-Agent`. The PR has
  `Closes #<n>` and a branch `factory/<n>-<slug>`.
- **Audit pause (ADR-0063 G5 (a)):** every `FACTORY_AUDIT_EVERY` (10) merged builder-app PRs since the last
  `Audit` issue closed by the owner's login (counted from GitHub), the dispatcher opens an `Audit` issue and takes no new task until
  the owner closes it. Fixes, rebases and reviews go on. Until M6 the audit itself is started by the owner. Only an
  `Audit` issue opened by builder-app counts, and only a close by the owner's login ends the pause, since
  builder-app and review-app hold Issues write too (security review round 2 of #0-286).
- **Started by a systemd timer** on the VM (every few minutes) instead of by hand (ADR-0060 D8 as amended).
- **Limits:** #0-261's GraphQL rate limit (points per hour, a backoff); #0-265 (a task back from Blocked is
  re-assessed by a read-only agent call before it is taken).
- **Where:** `factory`; builder-app gains Projects (organisation) read/write and Issues write.
- **Check:** whole runs against a fake GitHub:
  - the order above;
  - an expired lease;
  - two tasks at once with disjoint `touches`;
  - a rebase after the other's merge;
  - an issue edited by an outsider is not read;
  - an `Audit` issue is opened at the count, and no new task is taken while it is open.
