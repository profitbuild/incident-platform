## Parts, in order

### M6.1 The review rules split
- **What:** `.ai/rules/review/` splits into three parts:
  - the factory's core, which moves to `factory`;
  - the `spring-boot` profile, which moves to `factory`;
  - the product's own rules: tenants, Kafka, outbox. These stay here.

  The agents `review-*`, `verifier` and `acceptance-reviewer`, and the skill `review-procedure`, move to `factory`'s
  plugin.
- **With it, the build agents' profile:** what `factory`'s product-neutral build agents read about the stack (Maven
  and `-am`, Testcontainers), which #0-299 left in `.ai/rules/implementation.md`, moves into the same `spring-boot`
  profile, so the review and build agents read one profile.
- **Where:** `factory`, incident-platform (owner-only `.ai/rules/`, `.claude/`).

### M6.2 Reviewers without Bash (ADR-0063 G4)
- **Search without Bash, measured (M2.0, `m2.md` Record, measurement 2; Claude Code's tools reference, Glob
  section):** an agent whose `tools` leave out Bash keeps Grep and Glob; one that also names Bash loses them and
  searches through Bash. So a reviewer never gets Bash "as well": it would trade read-only search for a tool that runs
  code. The same holds for M6.4b's audit agents. Candidate for the call: `--restricted` (with `--strict-mcp-config`),
  which removes the tools that run code and `WebFetch` unless `--tools` names them, confines the file tools to the
  working directories and ignores user, project and local settings; measured first on the VM (M2.1). Under it the
  verifier's `WebFetch` allow-list cannot live in a project or user settings file. For the build zone ADR-0064
  (#0-300) puts every permission rule in managed settings, under which `--settings` and `--allowedTools` rules are
  ignored; whether the review zone's VM uses its own managed settings the same way is this step's to decide.
- **What:** each reviewer's tools become `Read`, `Grep` and `Glob`; the verifier
  also gets `WebFetch` to its allow-list. `review-procedure` stops calling `git`/`gh` and reads a workspace the
  dispatcher prepares:
  - `diff.patch`;
  - `base/` and `head/` with the changed files and their neighbours;
  - `issue.md` and `brief.md`;
  - `ci/` with test reports, coverage and `dependency:tree`, downloaded from the run's artifacts;
  - `findings-prev.json` for rounds 2+.
- **Check:** a planted instruction in a diff ("run …") reaches no tool that runs anything, because the init event
  lists none.

### M6.3 The review VM and review-app
- **What:** a Lima instance `factory-review`, provisioned like `factory-build` (one `provision.sh` with a role)
  without Docker or Maven. It holds git, gh, jq, Node and Claude Code, with egress to GitHub, Anthropic and the
  verifier's hosts. review-app is a GitHub App with Checks write, Pull requests write (comments), Contents read, Issues
  write (the `Audit` issue's report) and Projects write (the board's mirror of a review's result), installed on the
  product, never on `factory`; its key belongs to the review zone's dispatcher user.
- **Where:** `factory` (provisioning), GitHub (owner).

### M6.4 The dispatcher's review mode
- **What:** the same dispatcher, another kind of task:
  - **Picks:** a PR by builder-app, with CI green, no `factory/review` on its head, and no review running for it
    (one review per PR). A draft PR labelled `seed` is a seed run (M6.4b): reviewed the same way, its result
    published only as `factory/seed-review`.
  - **Runs:** the panel by paths, then the verifier on claims the panel could not check, then acceptance.
  - **Publishes:** with review-app, after reading the head again. A moved head gets only a comment.
    - Success sets `factory/review` = success on the SHA reviewed.
    - Findings set it to failure and add a comment in #0-262's format. The Project's `Changes requested` is only a
      mirror for the board; the build dispatcher reads `factory/review` itself (M5.1's trust rule), since review-app's
      Projects write must not make it trusted for the owner's inputs.
  - **Slots and limits:** two review slots, and a global limit on concurrent agent calls (6, with 429 backoff).
  - **After a rebase:** if `git patch-id --verbatim` of the whole `merge-base..head` diff, computed by the
    dispatcher, is identical, the verdict is carried to the new SHA without a model. The owner's approval and the
    human gate are never carried. Otherwise the change is reviewed by `git range-diff` of the old and new
    branch, not an old-head..new-head diff, which would hold `main`'s changes.
  - **Exempt from review AI:** a red CI.
- **Check:** whole runs against fakes:
  - a moved head;
  - an identical and a different patch id, and a whitespace-only change, which is not carried;
  - a seed PR's check run written by another app, which the build dispatcher ignores; a seed PR never gets
    `factory/review`;
  - two reviews at once.

### M6.4b Audits as task kinds of the dispatchers (ADR-0063 G5); `factory-ops` removed
- **`/audit` and `/docs-audit`, review zone:**
  - the agents (`audit-reviewers`, `audit-pipeline`, `audit-synthesis`, `review-docs` in audit mode) are read-only,
    without Bash, like the reviewers (G4);
  - the dispatcher prepares their data: PRs and labels from GitHub, the escape markers from the repository, the
    per-call trace of each PR body (M3.3), so the review zone needs no access to the build VM;
  - **the report goes into the `Audit` issue, written with review-app; the issue is work state only.**
    `/apply-audit` on the Mac:
    - reads the report as data, after checking that the body's last edit (`userContentEdits`) is review-app's or
      the owner's;
    - takes the owner's decision per recommendation (accept, reject, modify, defer), as today;
    - opens the owner's PR, which writes the report's text to `.ai/audit/<date>-<target>.md` and every decision to
      `.ai/audit/decisions.md`.

    The record stays in the repository (ADR-0055), and the acceptance rate keeps its denominator. No dispatcher acts
    on the report's text.
- **`/seed-bugs`, both zones:**
  1. the build dispatcher, in a task container: the seeder plants the pattern and the change compiles. The ground
     truth stays in the dispatcher's state, a stated exception to "dispatchers keep no state" (ADR-0063 G5);
  2. builder-app pushes `factory/seed-<run>` and opens it as a **draft PR labelled `seed`** (the owner's choice
     (3), review round 4 of #0-286). Its commit message and PR body do not name the pattern, since the PR is public
     while it lives. CI runs on it as on any PR, so the panel's `ci/` holds what a real PR's does, with no new
     permission and no change to CI;
  3. the review dispatcher takes it, with a green CI, by its label. It runs the panel and reports the findings as a
     **non-required check run of review-app** (`factory/seed-review`) on the head, with the findings as its JSON
     output, never `factory/review`. That check run is the one channel between the zones, through GitHub;
  4. the build dispatcher reads only that check run, and only if review-app wrote it. It scores the findings
     against the ground truth, appends the row to the series, closes the PR and deletes the branch. A series' rows
     reach `.ai/audit/benchmark/results.md` in the owner's PR, as today.

  A seed PR cannot merge: it is a draft, `main` requires `factory/review`, which it never gets, and the owner's
  approval holds until M12.
- **Trigger:** M5's audit pause opens the `Audit` issue. From here the review dispatcher fills it with the report.
- **Then removed:** `factory-ops`, `factory-ops-bash.sh`, ADR-0053's mechanism, the workflows `audit.js`,
  `docs-audit.js` and `seed-bugs.js`, and what only they used.
- **Where:** `factory` (the audit and seed modes), incident-platform `.claude/workflows/`, `.claude/agents/audit-*`,
  `defect-seeder`, `.claude/skills/apply-audit` (owner-only).
- **Check:** one `/audit`, one `/docs-audit` and one `/seed-bugs` run complete as task kinds; the seed PR stays a
  draft without `factory/review`, and its PR and branch are gone afterwards; the ground truth never reaches the review zone; nothing references
  `factory-ops`.

### M6.5 Required in the ruleset
- **What:** `factory/review` becomes required, bound to review-app by `integration_id`, and review-app is listed as
  an `Integration` where a ruleset needs it.
- **Where:** `.github/repository-settings/` (owner).

### M6.6 Lanes, trace, human gate (#0-295)
- **What:** jobs in GitHub Actions, not in either dispatcher:
  - `factory/lane` (low or high, from the task's `risk` and the changed paths; the higher wins);
  - `factory-trace` (`Closes #T`, T a sub-issue or legacy task, and the trailers agree);
  - `factory/human-gate` (low passes; high needs the owner's approval on the current SHA).

  CODEOWNERS keeps the owner on the high-risk paths (#0-153), and the catch-all stays until M12.

  The skill `/human-review <pr>` runs on the Mac in a fresh read-only clone. It summarises the change against its
  AC and brief, lists every finding (non-blocking ones included) and answers questions; the owner approves by typing
  the command.
- **Where:** incident-platform `.github/`, `.claude/skills/` (owner), `factory` (the skill's core).
- **Check:** the lane agrees with the owner on 3 PRs.
