# M8: planning and features (ADR-0055 stage 8), PLAN (written 2026-11-21)

The owner plans interactively on the Mac (ADR-0063 G3). A feature becomes a `Feature` issue with a brief and `Task`
sub-issues, built behind a flag, traced by trailers. Item: #0-297.

**Before:** M5's exit, and M6's for the trace check. While the repository is public, the pilot feature is a technical
one: no business brief goes into an issue before M9.

## Parts, in order

### M8.1 `bc-app`
- **What:** a GitHub App with Issues write and Projects write, without Contents write. Its key stays on the Mac and
  it mints hour tokens like `profitbuild-factory-dev` (#0-269). It is the only identity besides the owner whose
  issues a dispatcher reads (M5.1's trust rule).
- **Where:** GitHub (owner), `apps/bc-app.json`, `factory` (the token helper).

### M8.2 `/plan-feature` and `feature-planner`
- **What:** the three parts of ADR-0063 G3:
  - **The skill** holds the conversation. It reads the business repository and the code, and asks the questions it
    must always ask: what "done" means for the user; the scope and what is not done; ambiguous words, e.g. "resize"
    as a size limit or as compression; tenancy and authorisation; data that persists; an API contract.
  - **The agent** `feature-planner` takes the settled brief and returns JSON: tasks as vertical slices of one PR
    each, with AC, `touches`, Risk, Complexity, blocked-by and holdout ids. The first task is always the flag plus a
    walking skeleton; the last switches the flag on and removes it. In a `backend/` + `frontend/` repository the API
    contract comes first, so both sides can run in two slots.
  - **The script** writes the Feature, its sub-issues, the dependencies and the fields (as `bc-app`) in `Draft`.
    The skill sets `Ready` only on the owner's "ok".
- **Where:** `factory` (skill, agent, script), the product's adapter (its question list).

### M8.3 Feature flags
- **What:** a `FeatureFlags` interface in `shared`, reading `features.<name>.enabled`. A disabled feature returns
  404. Its tests run with it on. It is replaceable by an OpenFeature provider without changing callers. A flag is
  not a business rule: a plan-dependent limit is a policy class that stays.
- **Where:** incident-platform `shared` (all 7 services: `architecture.md`), with tests in `shared`.

### M8.4 Trace of a feature
- **What:**
  - the `Feature: #<n>` trailer and `factory-trace`'s check that T is a sub-issue of that feature;
  - `git log --grep "Feature: #<n>"` gives the feature's history;
  - a feature is Done when its sub-issues are closed, its holdout is green (from M10; until then its AC) and the
    flag's removal has merged.
- **Where:** `factory`, incident-platform `.github/` (owner).

## Exit
One technical feature planned with `/plan-feature`, built through the factory and Done.

## Not in M8
An autonomous planner. It enters when build slots stand idle for lack of Ready tasks; it would then run in the
review zone under a `planner-app` (Issues and Projects write, no Contents), and `Ready` would stay the owner's.
