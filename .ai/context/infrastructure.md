## CI gotchas

Concurrency (backlog #0-231): `ci.yml` and `factory-guards.yml` share one rule, `group: <workflow>-<PR number or
run_id>`, `cancel-in-progress` only off a push. A newer event of a PR (push, and in Factory guards a review) cancels
its older run; a push to `main` is never cancelled, because main-guard.yml and `preflight.sh` read every push's own
run (#0-148). It takes its own group (`run_id`) rather than only `cancel-in-progress: false`, since GitHub cancels a
*pending* run of a shared group whatever that flag says: never simplify the group to `github.ref`. A new workflow
that runs on `pull_request` takes the same block.

`.github/workflows/ci.yml` runs build+test (skipped, like the smoke test, on a pull request that changes only
Markdown, at the job so a required check still passes; always on a push to `main`; nothing the build, its tests
or its check scripts read is Markdown, so a new check that reads one must change the `code` filter in
`detect-changes`), Kustomize+kubeconform validation of base and all three overlays, `lint-workflows` (first the pinned CI tools, backlog #0-147, ADR-0033: the tests of `install-pinned-tool.sh` and `check-pinned-tools.sh`, then every tool pin in every workflow checked against its publisher; then backlog #0-146, ADR-0032: actionlint on every workflow and its calls of local actions, every workflow `run:` block through shellcheck, never the runner's shellcheck nor `download-actionlint.bash`, any finding fails it, there is no ignore list; then backlog #0-149: `check-shell.rb` runs the same shellcheck on every tracked `.sh` file and every composite action's bash/sh step, every severity (SC2086 is a note), `--norc` (a `.shellcheckrc` is on no protected list, and shellcheck reads one from any directory above a script), so a meant finding is disabled at its line with its reason on the line above, never by an exclude or a severity floor, and a new script is checked only if it is a tracked `.sh` file; `check-downloads.rb` refuses curl, wget, a release asset's URL or `gh release download` in any `run:` block unless the line ends `# not-a-download: <why>`; then backlog #0-268: `check-factory-copies.rb` compares `profitbuild/factory`'s copies (tool pins, actions' SHAs, `install-pinned-tool.sh`, `secret-scan.sh`, `test-secret-scan.sh` minus their notice, the item lock's cases `.github/scripts/fixtures/item-lock-branches.tsv` at a path of its own there (`MOVED_COPIES`, #0-278 AC11), `setup-node` and `zizmor.yml` minus their comments, `.node-version`, the denies both ways) with this repository's, on a fresh clone of `factory@main` (ADR-0061): a pull request that changes a compared file fails on a difference it brings and `main` (HEAD^1) lacks (this repository leads, so the owner mirrors the change in `factory` first), every other difference and run only warns, a symlink in the clone fails it and a parse error is never quoted (SEC-31), and `check-downloads.rb`, `check-runtime-setup.rb`, `check-shell.rb` run on the clone as warnings; each checker's cases run first; then zizmor, #0-147: a security audit of the workflows and the composite actions' `action.yml`, default persona, offline, any finding not suppressed fails it, and a suppression names its reason, inline next to the line or in `.github/zizmor.yml` for an audit turned off; then `repository-settings.rb check`, backlog #0-113, ADR-0034, ADR-0035: GitHub against `.github/repository-settings/` (ruleset, environments, settings, admins, which secrets exist), every secret a job reads inside an environment that holds it, and every job of a pull request's workflows is a required check and the other way round, so a job added, renamed or given a path filter changes `rulesets/main.json` in the same PR, then the owner `apply`s it; last, even when a step above is red, backlog #0-278 (ADR-0061, amended): "The adapter keeps its factory version's schema" clones `factory` at `.factory/adapter.json`'s `factoryVersion` tag (`refs/tags/` explicitly), fails unless that tag's commit is `provision.sh`'s `FACTORY_COMMIT` (two pins of one version until #0-307: moving `FACTORY_COMMIT` needs the tag created first, by the admin) and checks the adapter with that version's own `checkAdapter`, after every step that holds a token, since it runs `factory`'s code), then backlog #0-280 (ADR-0061, amended): "The test gate's answers keep factory's contract" runs `test-run-tests.sh` with `FACTORY_CHECKOUT` at that checkout, and `check-gate-answers.mjs` holds every answer its cases make, the real output of each path of `run-tests.sh`, to that version's own `checkGateAnswer`, the dispatcher's (a canary answer the checker must refuse first; exit 1 a refusal, 3 a check not made): a difference always fails, so a change of `run-tests.sh`'s answer, or a move to a version whose contract differs, fails this job until the two match; Factory guards runs the same test with `FACTORY_CHECKOUT` unset (no network locally), which runs the checker's own cases and skips the contract, `secret-scan` (backlog #0-109, ADR-0036: pinned betterleaks with its default rules on every commit a pull request adds, `base..head`, and a push brings to `main`, `before..after`, not the tree; `secret-scan.sh` fails on a `.gitleaks.toml`/`.betterleaks.toml` or a `.gitleaksignore`/`.betterleaksignore` at the root, so a finding that is no secret gets `gitleaks:allow` and its reason on its own line, and a test that needs a secret-shaped value builds it at run time; its cases run first), a docker-compose smoke test that boots Postgres/Redis/Kafka, the log pipeline (docker-socket-proxy, Loki, Alloy) plus all 7 services and curls each health endpoint (then checks the services' DB role, backlog #0-78, and that every service's lines reach Loki parsed and `docker-socket-proxy` refuses writes on an internal network, `.github/scripts/test-log-collection.sh`, #0-94 step 2, whose `curlimages/curl`/`alpine` tags live only in that script; `docker-compose.yml` requires `DB_PASSWORD`, `POSTGRES_ADMIN_PASSWORD` and `GRAFANA_ADMIN_PASSWORD`, so the job sets them in its job-level `env` — every compose command, teardown included, interpolates them), `postgres-roles` (`.github/scripts/test-postgres-roles.sh`: the Postgres init script and `docs/database-roles-migrate.sql` against the image named in `docker-compose.yml`; plus `.github/scripts/check-db-password-config.rb` and its bypass test `test-db-password-config.sh`: every committed `spring.datasource.password` is exactly `${DB_PASSWORD}`, no literal or defaulted datasource/Flyway password, backlog #0-66), and `validate-monitoring-config` (backlog #0-16): `promtool check config` + `promtool test rules docker/prometheus.rules.test.yml`, `amtool check-config` + `amtool config routes test` assertions on `docker/alertmanager.yml` (Watchdog reaches only the dead man's switch, critical platform alerts reach both operator email and the webhook), and `loki -verify-config` + `alloy validate` + `alloy fmt` (canonical form required) on `docker/loki.yml` and `docker/alloy/config.alloy`. The smoke test never starts Prometheus/Alertmanager, so this job is the only check of that config. It runs the `prom/prometheus` / `prom/alertmanager` images pinned by tag in the job itself, and those tags must equal the ones in `docker/docker-compose.yml` — bump both together (the `grafana/loki` / `grafana/alloy` tags it reads from the compose file itself, #0-94 step 2), or CI validates against a different version than compose runs. A change to a route or receiver in `alertmanager.yml` usually needs a matching `routes test` line in the job. Ten structural rules it enforces (the five listed, then the sixth to the tenth below; a new rule is added
after the tenth, as CLAUDE.md and ADR-0023 cite the sixth by its number):

- Every directory with a `Dockerfile` must have a matching Deployment in `k8s/base` (name-matched in the rendered manifest).
- A new runnable service must parent to `service-parent`, not the root POM — that's where `spring-boot-maven-plugin` is declared, and without it the jar is not repackaged (no `Main-Class`/`Start-Class`, no `BOOT-INF/layers.idx`), so the image's `jarmode=tools extract` fails at build time (until #0-141 the image ran `java -jar app.jar`, which failed with "no main manifest attribute"). `shared` deliberately stays on the root parent.
- Mail in k8s (backlog #0-42, ADR-0026, `.github/scripts/check-k8s-mail.rb`): only the dev overlay has Mailpit (ClusterIP, never exposed) and the `SPRING_MAIL_PROPERTIES_*` overrides; the Mailpit image tag must equal `docker/docker-compose.yml`'s (bump both); the dev JVM patches must keep `labelSelector: app.kubernetes.io/component=backend`, and a new infrastructure Deployment in dev needs another component value.
- Each k8s overlay deploys its own environment (backlog #0-29, `.github/scripts/check-k8s-environments.rb`, with its mutation test `test-k8s-environments.sh`): every resource of the dev, staging and prod renders is in `incident-platform-<overlay>`, and prod runs no untagged or `latest` image and no service tagged with an environment's name (`dev`, `staging`, `prod`) — a release tag or a digest. The same script keeps the HPAs the only owner of the services' replica counts (backlog #0-137): in every render each `component=backend` Deployment has an HPA aimed at it, that Deployment sets no `spec.replicas` (each `kubectl apply` would reset what the HPA scaled to), and `minReplicas` is not above `maxReplicas`; in prod every HPA's floor is at least 2. It also keeps that floor safe from the cluster (backlog #0-138, ADR-0029): in every render each service is covered by exactly one PodDisruptionBudget, with `maxUnavailable: 1` (never `minAvailable`, which at the floor blocks every drain) and `unhealthyPodEvictionPolicy: AlwaysAllow`, and its pod template spreads over `kubernetes.io/hostname` with `ScheduleAnyway` (a hard rule leaves pods Pending on a cluster with fewer nodes than pods). Size an environment by patching its HPAs' `minReplicas`/`maxReplicas` in the overlay, never `spec.replicas`, and keep the ceilings within backlog #0-79's connection arithmetic (ADR-0028). It reads the renders, not the files: kustomize's top-level `namespace:` overrides what every resource declares, each overlay's `secrets.yml` included (history: README "Infrastructure Hardening").
- The rendered staging and prod k8s overlays set no Spring profile, in any form (backlog #0-63): only `k8s/overlays/dev` sets `SPRING_PROFILES_ACTIVE`, because the dev profile enables incident-service's unauthenticated `/dev/token`. A real prod profile would need that check changed on purpose.

The sixth (backlog #0-94): no tracked YAML, properties, JSON, `.env`, Dockerfile, shell script or Makefile (docs, `shared/src/test` and the check's own scripts aside) names `platform.logging.plain-text` (the usual spellings: `plain_text`, `plainText`, `PlainText`, the variable `PLATFORM_LOGGING_PLAINTEXT` in any case, flow style, quoted, escaped in JSON, an argument; Kafka's `PLAINTEXT` is not matched), the one switch `StructuredLoggingGuard` lets through to plain-text logs, and no service ships a `logback*.xml`/`.groovy` in `src/main/resources`. The guard, not this check, is what holds: any other way of switching JSON off already makes the service refuse to start, which the smoke test would show; the check catches the switch committed by mistake. Only tracked files are read, so a developer's gitignored `application-local.yml` may carry the switch. "Build, Test & Coverage" runs `.github/scripts/check-structured-logging.sh` (after its own cases, `test-structured-logging.sh`).

The seventh (backlog #0-81): no Spring profile configuration, and no literal secret, is committed under `src/main/resources`: it would ship in every jar and image. "Build, Test & Coverage" runs `.github/scripts/check-packaged-profiles.sh` (after its own cases, `test-packaged-profiles.sh`), which fails on a committed `application-<profile>.*` there, a base `application.*` with a `spring.config.activate.on-profile` key or a `spring.profiles.active` / `include` / `default` / `group`, or a key ending in `secret`, `encryption-key`, `private-key` or `api-key` (any case, kebab or camelCase) that is not a `${VAR}` without default. It has no allow-list: a profile in a jar needs a backlog decision and a change to the script. Test configuration goes in `src/test/resources` or `@TestPropertySource`; deployed configuration comes from the environment; the developer's `application-local.yml` stays gitignored.

The eighth (backlog #0-82): every directory with a `Dockerfile` except `auth-service` sets `auth-service.base-url` from `${AUTH_SERVICE_URL}` in its `application.yml`, or the service silently gives every tenant full access, suspended or not. "Build, Test & Coverage" runs `.github/scripts/check-tenant-status-config.sh` (after its own cases, `test-tenant-status-config.sh`).

The ninth (backlog #0-100): no jar holds a developer's gitignored local configuration (`application-local.*`, `application-secrets.*`: their real local secrets). The root POM excludes both from every jar (`maven-jar-plugin`, so `shared` too; the files are still copied to `target/classes`, which `spring-boot:run` reads). "Build, Test & Coverage" plants both in every service and in `shared` before compiling; `.github/scripts/check-no-local-config-in-jars.sh` (after its own cases, `test-no-local-config-in-jars.sh`) fails if any `*-service-*.jar`, or the one `BOOT-INF/lib/shared-*.jar` nested in it, contains one or cannot be read. The smoke test also runs `docker compose run auth-service break-glass-mfa-reset` without options and expects its refusal (exit 1): the proof that `JarLauncher` passes arguments to `main`.

The tenth (backlog #0-145, ADR-0031): the Maven caches go through `.github/actions/restore-maven-caches` and `save-maven-caches` only. "Build, Test & Coverage" runs `ruby .github/scripts/check-maven-caches.rb` (after its own cases, `test-maven-caches.sh`), which reads every workflow and action and fails on: a cache step (`actions/cache`, `/restore`, `/save`, or setup-java with `cache: maven`) of `~/.m2` outside the two actions, OWASP Dependency-Check's data (`~/.m2/repository/org/owasp/`) excepted; `~/.m2/wrapper` cached with another path or restored with `restore-keys`; `~` or `~/.m2` (or a glob that can match `~/.m2/wrapper`) in the actions; a save whose path list is not the restore's (the path list is part of an entry's version); a distribution key that does not hash the properties, `check-maven-wrapper-sum.sh` and both actions. An unreadable file or a missing action fails too.

The images (backlog #0-141, ADR-0030): build once, package many. CI compiles and resolves dependencies only in build-and-test, which uploads the jars `verify` tested as the `service-jars` artifact (uncompressed, and only under the smoke test's own `if:`, which the upload step repeats: keep the two equal); the smoke test downloads it into each `<service>/target/` and is the only job that builds images. Each Dockerfile only packages that jar (`COPY <service>/target/<service>-*.jar jar/`, exactly one or the `RUN` fails; `jarmode=tools extract --layers --launcher`; four `COPY` layers; `ENTRYPOINT` `JarLauncher`, which still passes arguments to `main`, as auth-service's `break-glass-mfa-reset` needs; files root-owned, not writable by `appuser`) and never runs Maven, so nothing downloads from Maven Central in Docker. `.dockerignore` is an allowlist of those jars alone. Locally `make dev-up` runs `make build` first and `compose up --build`; plain compose packages whatever is in `target/`. A new service's Dockerfile follows the same shape. The Maven caches (backlog #0-145) are restored only through `.github/actions/restore-maven-caches` (every job that runs `./mvnw`) and saved only through `save-maven-caches` (build-and-test, on a push to `main`): their paths and keys are written there and nowhere else, and the tenth structural rule refuses any other cache of `~/.m2` (OWASP Dependency-Check's database under `~/.m2/repository/org/owasp/` excepted). The repository cache (`~/.m2/repository` only, prefix `maven-repo-`, POMs' hash, restored by prefix within the month) is `actions/cache`, not setup-java's `cache: maven`, which restores only an exact match of the POMs' hash and so re-downloaded everything on every dependency bump. `.mvn/maven.config` retries 429/500/502/503/504 for every `./mvnw`. The Maven distribution (backlog #0-142, ADR-0031): `./mvnw` at the root is the only wrapper (never add one to a module) and is pinned by `distributionSha256Sum`; `check-maven-wrapper-sum.sh` checks that sum against Apache's SHA-512 whenever build-and-test's `~/.m2/wrapper` cache misses. That cache has an exact key and never `restore-keys`, and `~/.m2/wrapper` never goes back into the repository cache (both enforced by the tenth rule): mvnw does not check a distribution it finds unpacked. A Maven bump by hand takes its sum from a zip checked against Apache's `.sha512`.

Every workflow under `.github/workflows/` declares its own `permissions:` at workflow level (backlog #0-59) instead of relying on the repository's "Workflow permissions" setting: read-only (`contents: read`), or `{}` when no job may inherit even that (`main-guard.yml` and `signing-keys.yml`, whose one job each asks for `issues: write`; backlog #0-147, #0-152). A job that needs more declares its own block, which replaces the workflow's, so it repeats `contents: read` if it needs it. A job that runs a PR's own code never gets a write scope. No check enforces this — review does.

Every `uses:` is pinned to a full commit SHA with its tag in a comment (`owner/action@<sha> # vX.Y.Z`; backlog #0-60), and every `actions/checkout` sets `persist-credentials: false`. The repository setting `sha_pinning_required` is on (since 2026-09-29, after the #0-60 PR merged and `main`'s run was green), so a workflow with a tag-pinned `uses:` fails to start — current state in README "Infrastructure Hardening", how to resolve a SHA in ADR-0020 (`.ai/decisions/`).

Factory guards (`.github/workflows/factory-guards.yml`, a required check) runs on every pull request, Markdown-only
ones too, so a check of Markdown belongs there, not in build-and-test. `check-rule-claims.rb` (backlog #0-184) reads
the review rule files and `.ai/audit/benchmark/patterns.md` against the workflows and the ruleset of `main`: an
"Enforced by" label must name a script that a step of a required job runs on a pull request (a step or job whose
`if:` leaves pull requests out or that continues on error, and the "Changes that need the owner" step, do not
count), or such a job by its id (ADR-0046).
Moving such a script, renaming a required job or retiring a rule id a pattern cites fails it.

Security scans (OWASP Dependency-Check, Snyk) run in separate workflows. Every tool CI downloads from a GitHub release (the Snyk CLI, kubeconform, actionlint, shellcheck, zizmor, betterleaks; backlog #0-147, ADR-0033) is a pin in its job's `env`: `# renovate: datasource=github-release-attachments depName=<owner/repo> verify=<method>`, then `<NAME>_VERSION: <release tag, with its v>` and `<NAME>_SHA256` (one `<NAME>` for both), the only form `check-pinned-tools.sh` accepts for a `*_SHA256` line. It is installed only through `.github/scripts/install-pinned-tool.sh`, never a `curl | tar` of its own (lint-workflows' `check-downloads.rb` refuses one in a `run:` block, backlog #0-149; a curl that is not a download, like the smoke test's health probe, ends its line with `# not-a-download: <why>`). Renovate bumps tag and SHA-256 together (its own PR per tool, after 7 days), computing the SHA-256 from what it downloaded, so lint-workflows' `check-pinned-tools.sh` checks every pin on every run: GitHub's digest of the asset, then `verify=`: `attestation` (actionlint, zizmor), `release` (betterleaks: `gh release verify-asset`, the asset in an immutable release's attestation, ADR-0036), `gpg:<fingerprint>` (the Snyk CLI: its release's `sha256sums.txt.asc`, signed by the key committed as `.github/keys/<fingerprint>.asc`; a new key is a new file, checked against Snyk's docs, the snyk/cli repository and keys.openpgp.org; see the expired-key rule below), `checksums:<file>` (kubeconform's `CHECKSUMS`), `digest` (shellcheck, which signs nothing). A new tool takes the strongest its publisher offers. The Snyk token is set only on the scan step (backlog #0-61), and both `snyk.yml` jobs run `check-pinned-tools.sh --expect 1 .github/workflows/snyk.yml` before installing the CLI (`--expect`: a pin renamed out of the `_SHA256` form is not seen, so the count must match): a tool that receives a secret is checked where it runs, not only on its pull request (ADR-0033, ADR-0034). The k8s job pins its other inputs by hand (backlog #0-76, ADR-0027), in its own `env` in `ci.yml`: `KUBECONFORM_SCHEMA_LOCATION` naming a commit of `yannh/kubernetes-json-schema` (never `master`), and one `KUBERNETES_VERSION` for both the kubectl that renders and the schemas — bump it only to a version whose `v<version>-standalone-strict` directory that commit has, and compare the renders before and after (a newer kubectl bundles a newer kustomize). CLAUDE.md's local command reads those values from `ci.yml`. kubectl itself is pinned by version only (`azure/setup-kubectl` verifies nothing; signature check: #0-135). The runtimes are pinned by their setup actions: Java 21 (`setup-java`), Python 3.13 (`setup-python`, diff-cover) and, since backlog #0-166 (ADR-0040), Ruby from `.ruby-version` through the local action `.github/actions/setup-ruby` (the only `ruby/setup-ruby`, no `ruby-version` input; it prints Ruby's, json's and psych's versions), right after checkout in every job that runs Ruby: build-and-test, validate-k8s-manifests, lint-workflows, postgres-roles, Factory guards. Node likewise since #0-163 (ADR-0043): `.github/actions/setup-node` (`actions/setup-node`, pinned by SHA, the version in `.node-version`, Node's built-in modules only, no npm) in Factory guards (the tests) and lint-workflows (whose `test-runtime-setup.sh` names `node` in its cases). A new Ruby or Node step needs its action before it in its job, or lint-workflows' `check-runtime-setup.rb` fails (otherwise it would run on the runner's unpinned Ruby and gems, whose json gem once changed a check's result, PR #517). `.ruby-version` and `.node-version` are on the build-config list of `protected-paths.md`. The `.rb` checks run on that Ruby only (no promise for the macOS system Ruby since #0-166 PR 2): locally through `.github/scripts/ci-local.sh`, which runs lint-workflows' and Factory guards' own `run:` steps (`ci-local-steps.rb`, tested by `test-ci-local.sh` in Factory guards) in an image `FROM ruby:<.ruby-version>-slim-trixie` with the `node` binary of `node:<.node-version>-trixie-slim` (the same Debian, #0-163), both jobs native (on an arm64 Mac only the pinned x86_64 linters are emulated, through Rosetta; the image adds `libc6:amd64` for zizmor's glibc build), the tree handed over as a tar of the files git does not ignore (no mount: an ignored `docker/.env` or `application-local.yml` never reaches a step) with `.git` whole, so the run is refused while the stash is not empty or the repository's git config holds credentials, and inside a container (the devcontainer's Docker is the host's); factory-guards runs with `--network none`; a step that needs a `${{ }}` value (the event, a token) is skipped there whole, so token-free work belongs in a step of its own (as `test-repository-settings.sh` is). Unfixable CVEs are suppressed with a justification and expiry in `owasp-suppressions.xml` / `.snyk`; dependency version overrides for CVEs live in the root `pom.xml` properties with a comment naming the CVE.

An expired signing key passes only a pin that was on main before the key expired: at the last merge commit of the first-parent history dated before the expiry, so lint-workflows and both `snyk.yml` jobs check out with `fetch-depth: 0`, and a rebased or squashed commit's own date never counts; the signature must predate the expiry, and a revoked key (gpg's `REVKEYSIG` or `KEYREVOKED`, or `r` on the key) refuses every pin (backlog #0-152). Each key has a `<fingerprint>.source` naming the publisher's file: lint-workflows checks offline that it exists, and `signing-keys.yml` compares the key with it every Monday, turning a rotation, a revocation, an extension or a failure to look into one issue labelled `security`.

## Log pipeline (docker-compose)

> Moved verbatim from `CLAUDE.md` "Conventions" (Logs) on 2026-11-12, for the same reason as the rest of this file;
> `CLAUDE.md` keeps the format and secrets rules and points here.

In docker-compose, Alloy ships every `incident-*` container's lines to Loki (15 days, read in Grafana; #0-94 step 2):
labels only `service`/`container`/`level`, the MDC ids as structured metadata, never labels (a stream per value);
Alloy reads the Docker API only through `docker-socket-proxy`, never the socket; Loki and Alloy (no authentication)
are on the internal `logs` network with Grafana and Prometheus only (Alloy also on the internal `docker-api` network,
with the proxy alone), and none of the proxy, Loki, Alloy and Grafana is on `default` (Grafana there would be a way
around `logs`; the smoke test checks it); Loki's delete API is off.
